## The five declared deviations

**1. `matchesFilter` exported from `@pariksha/core` — justified as a decision, not as a signature.**
Duplicating the draw arithmetic was genuinely worse, and `select.ts`'s own
pre-existing comment already made the argument: "an import-time *this pool is
too small* that disagreed with the run-time `PoolTooSmallError` would be
worse than no check at all." Exactly the same sentence covers a builder count
that disagrees with the engine, so the honest move was to export it rather
than to let `apps/api` guess. It also does not widen core's surface in a way
that will be regretted in the usual sense: `matchesFilter` is pure, reads
three fields, has no state, and `selectForSection` — the one that really is
internal — stayed internal.

The half that is not justified is the **signature**. It takes `Question`, the
whole document type, and the only external caller holds a `QuestionSummary`
and writes `q as unknown as Question` twice (`routes/tests.ts:174`, `:193`).
The cast is sound today only because `matchesFilter` happens to read
`tags`/`difficulty`/`type` and because `difficulty: Difficulty | null`
happens to fail the `=== undefined` test with the right answer. Widen the
parameter to `Pick<Question, "tags" | "difficulty" | "type">` and have
`workspaceQuestionSummaries` map `difficulty: row.difficulty ?? undefined`,
and both casts and the whole class of future divergence go away. **I6.**

**2. `workspaceId` on `draft()`/`patchDraft()` and on the two components — justified; the correction is right and the plan is the thing that is wrong.**
Every sibling takes the workspace first: `test(workspaceId, testId)`,
`updateTest(workspaceId, testId, patch)`, `listQuestions(workspaceId,
bankId, filter)`, `deleteQuestion(workspaceId, …)`. The route is
`/api/v1/workspaces/:id/tests/:testId/draft` and the client has no ambient
workspace, so the plan's sketch could not have compiled. `SectionList` and
`QuestionPickerDrawer` genuinely need `client`+`workspaceId` — the bank
`<select>` and the question list are both workspace reads — and both were
added additively with every planned prop unchanged. Corrected signatures are
below.

**3. Two `getDraftVersion` reads per PATCH — justified as a contract; flagged as a budget.**
`putDraftVersion` taking a whole `TestDocumentBody` is the right call and
should **not** become a patch. The merge is Review Focus 3's actual subject:
which keys replace and which survive is route policy, it differs per block,
and pushing it into a repository function would put the one rule this task
exists to get right behind a layer that cannot see the request. The existing
`updateTest`/`TestPatch` split is the same arrangement. Two indexed single-row
reads against a 50-subrequest ceiling is not a cost worth trading for that,
and documenting it in `app.ts` rather than hiding it is correct.

The flag is that the measurement only ever exercises the UPDATE branch. The
INSERT branch is three reads, not two, and it becomes reachable the moment
Task 11 publishes — see **I8**. One `?? existing` parameter on
`putDraftVersion`, or a `createDraftVersion` sibling, closes it without
touching the contract.

**4. The per-section `points` field — justified, in scope, and in fact required by the plan's own test.**
`UX-12`'s collapsed row is literally "*title · source · question count ·
points · time*", `docs/design.md:211-214` names points as the reason the row
exists, and the plan's own Step 1 test asserts
`/… · 4 questions · 8 points · 15 min/i`. No channel in the plan's
`Interfaces` block delivered that number, so this is a plan defect the
implementer had to fix to satisfy the plan's own red test. Adding it to the
same GET is the right place.

"Zero extra cost" is **true for queries** — no extra statement, confirmed by
`draft.test.ts:388` measuring 4 — and slightly overstated for CPU, since the
pool branch re-runs `matchesFilter` over the bank-filtered list that `draw`
just filtered, then sorts it. That is immaterial. What is not immaterial is
that the pool figure is a fabricated draw presented without qualification:
**I3**.

**5. The repo-wide `ignoreRestSiblings` — justified.**
It is the narrower of the two available relaxations. The broad one,
`varsIgnorePattern: "^_"`, would silence every unused variable anyone chose
to underscore; `ignoreRestSiblings` silences only siblings of a rest element,
which is the one construct in question and is why the option exists. No other
option is weakened — `args: "after-used"` and `caughtErrors: "all"` stay at
their defaults, and `no-explicit-any` is untouched. It is also not one call
site: four already (`test-document.ts:106`, `SectionList.tsx:264`, `:464`,
`:503`) and every later panel that drops an optional key under
`exactOptionalPropertyTypes` will add another. One ride-along nit: with the
option on, the `_drop`/`_schema` prefixes are now redundant.

## The undeclared sixth deviation

**`schemas/test-1.json` was replaced by a hand-written field-name check, and
only for `sections`.** The plan's "Save-time versus publish-time" paragraph
names the schema parse as a save-time rule and gives the reason
(`additionalProperties: false`). The implementation substitutes
`SECTION_FIELDS`/`SOURCE_FIELDS` name comparison for `sections` and nothing
at all for `settings`, and the substitution is explained in a code comment
rather than declared as a deviation.

The stated justification — that `minItems` on `sourceFixed.questions` and
`sourceSets.sets` would reject the UX-13 empty section — is **correct and
load-bearing**; running the schema unmodified would indeed break UX-13. It is
not a reason to drop `type`, `required`, the `^[a-z0-9_-]{1,40}$` id pattern,
`count`'s `integer`/`minimum`, or every one of `$defs/timing`,
`$defs/access`, `$defs/scoring`, `$defs/release`. `@cfworker/json-schema` is
already a dependency and `apps/api/src/import/schema.ts` already wraps it and
already maps its `OutputUnit`s into the repo's own issue shape. A derived
schema — the same document with the three UX-13 floors removed — reuses all
of it. **C1, C2, I1.**

## The four independent verifications

**Review Focus 3, the merge bug — the claim holds, and both halves are pinned.**
Traced by hand. Against a naive per-section deep merge, the second PATCH in
`draft.test.ts:169-205` sends `source: {kind:"pool", bank, count:4}` over a
stored `{kind:"sets", assignment:"round_robin", sets:[…]}`; the merged source
keeps `assignment` and `sets`, `JSON.stringify(body.body)` contains
`"round_robin"`, and the assertion at `:202` fails. Note the structural
check cannot save a naive merge here, because `checkSection` runs on the
incoming patch, not on the merged result. The test distinguishes.

The settings half is better than the plan asked for. `draft.test.ts:207-227`
fails in **both** directions: against a lodash-style deep merge, `OLD1`
survives under `access` and `:226` fails; against a whole-`settings` replace,
`timing` is dropped and `:217` fails. Only the one-level `Object.assign`
at `routes/tests.ts:434-437` passes both. `:253-264` adds a third,
hand-built case so the structural guard is proven independently of the merge.
This is the one part of the task that is unambiguously right.

**The reachability test — present, correct, and the first time this phase has got it right.**
