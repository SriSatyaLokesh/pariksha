Band 3 · The thesis — the sequencing decision, argued rather than disclosed · 150 words

The format came before the software, on purpose.

Most exam platforms hold your questions in a database you cannot read, behind an export button someone else designed. Pariksha published the file format first — pariksha/question@1 and pariksha/test@1, with JSON Schemas, a worked example and a validator — and is building the software against it.

That ordering has one consequence worth the whole page: the questions you write today outlive any tool, including this one. They are plain documented JSON under CC BY 4.0. You can diff them in git, review a question set in a pull request, generate them from a spreadsheet, or hand the bank to someone who has never heard of Pariksha.

It also means there is something real to use before the application exists. The format is stable now. The validator runs now.

git clone https://github.com/SriSatyaLokesh/pariksha.git
cd pariksha

npx -y -p ajv-cli@5.0.0 -p ajv-formats@2.1.1 ajv validate --spec=draft2020 \
  --strict=false -c ajv-formats -s schemas/bank-1.json \
  -r schemas/question-1.json -d "examples/*/questions.json"

Write your own questions, validate them, and they will import into Pariksha on day one.

Band 4 · What you get — tagged per feature, never per page · 220 words

Twelve question types, five scoring modes, one open file.

Question types live

Single, multiple, select exactly K, true/false, assertion–reason, matching, multi-matching, ordering, fill in the blank, numeric with tolerance, short and long answer.

Scoring live

All-or-nothing, partial credit, negative marking, ordering by position, rubrics. Applicable modes are enforced per type, so an invalid combination cannot be entered.

Selection live

Pool draws filtered by tag and difficulty, fixed sets A/B/C assigned round-robin, seeded shuffling that survives a refresh, pinned options that never move.

Validation live

Cross-field import rules: keys must exist among the options, every blank needs a row, sets must balance on points. One bad question imports nothing.

Authoring and the runner v0.1

The bank browser, the question editor, the test builder, the candidate runtime and three proctoring profiles.

API and results v0.1

REST under /api/v1, signed webhooks, the live monitor, the grading queue, item analysis and the results CSV.

Everything marked live is implemented and unit-tested in packages/core, gated in CI. Everything marked v0.1 is specified in the PRD and the interaction design, and not yet built.

Band 5 · Architecture — the evaluator's band · 140 words

One codebase, two deployment targets, three adapter seams.

The API and all scoring logic are plain TypeScript written against three interfaces — database, object storage, identity — so the same code runs on Cloudflare Workers or in a Docker container. Answer keys, timing and permissions are enforced only on the server.

Candidate browser ─┐
                   ├─→ Pariksha API ─→ D1 · SQLite · Postgres
Organiser browser ─┘                └─→ R2 · S3 · disk
                                     └─→ OIDC · email · captcha

Cloudflare free plan today; Docker with Postgres, MinIO and Caddy is Phase 11. Moving between them is configuration, not a rewrite — which is also the mitigation for the one named risk against the zero-cost estimate: free-tier limits can change.

Band 6 · Integrity — the position no proctoring vendor can copy · 170 words

Integrity without surveillance: no video, no audio, no verdicts.

Strict proctoring takes a 320×240 snapshot about every sixty seconds, counts faces on the device itself, and stores no biometric template. Nothing is streamed and nothing is recorded. Snapshots live in your own bucket behind links that expire in ten minutes.

Pariksha marks an attempt clean, review or high risk — and stops. Browser checks deter and record; they cannot prove. A second phone is invisible to every one of them, and the documentation says so. That is exactly why no machine here is allowed to reach a verdict.
