# Pariksha test format (`pariksha/test@1`)

A test is one JSON file: identity, timing, access, registration form, proctoring, scoring, sections and result release. It is what `GET /tests/{id}/export` returns and what import accepts, so a test built on one Pariksha installation runs unchanged on another.

Questions live in a separate [bank file](question-format.md); a test refers to them by ID.

- **Schema:** [`schemas/test-1.json`](../schemas/test-1.json) (JSON Schema draft 2020-12)
- **Worked example:** [`examples/reasoning-aptitude/test.json`](../examples/reasoning-aptitude/test.json), explained screen by screen in [that folder's README](../examples/reasoning-aptitude/README.md)

## Shape

```json
{
  "$schema": "../../schemas/test-1.json",
  "format": "pariksha/test@1",
  "name": "Reasoning and Aptitude Screening 2026",
  "slug": "reasoning-aptitude-2026",
  "banks": ["questions.json"],
  "timing": { },
  "access": { },
  "consent": { },
  "registration_form": { },
  "proctoring": { },
  "scoring": { },
  "sections": [ ],
  "release": { },
  "retention": { }
}
```

`format`, `name`, `slug`, `timing` and `sections` are required. Everything else has a default.

## Identity

| Field | Description |
| --- | --- |
| `name` | Up to 120 characters, shown to candidates |
| `slug` | Lowercase letters, digits and hyphens; unique per workspace. The candidate URL is `/<workspace-slug>/<test-slug>` |
| `description` | Markdown, shown on the landing page |
| `tags` | For filtering the test list, e.g. `["campus", "screening"]` |
| `banks` | Bank files this test draws from, relative to the test file |
| `license` | SPDX identifier for the content, e.g. `CC-BY-4.0` |

The immutable `tst_` ID, short link and QR code are generated by Pariksha and are not part of the file, so an exported test can be imported anywhere without colliding.

## `timing`

| Field | Default | Description |
| --- | --- | --- |
| `timezone` | instance default | IANA zone, e.g. `Asia/Kolkata`. Every time shown to a candidate uses it |
| `opens_at`, `closes_at` | — | The availability window, as RFC 3339 timestamps |
| `latest_start_at` | `closes_at` | Nobody may start after this |
| `duration_minutes` | **required** | Length of one attempt |
| `navigation` | `free` | `free` jump anywhere · `linear` no going back · `per_section` free inside a section, locked once left |
| `attempts_allowed` | `1` | |
| `cooldown_minutes` | `0` | Wait between attempts |
| `counted_attempt` | `highest` | `highest`, `latest` or `average` |
| `warn_at_minutes` | `[10, 2]` | Countdown warnings |
| `late_sync_grace_seconds` | `30` | Answers arriving later than this after the deadline are rejected |

The deadline is set and enforced on the server. Changing the computer's clock does nothing.

## `access`

| `mode` | How the candidate gets in | Also set |
| --- | --- | --- |
| `link_code` | Public URL plus a code announced in the room | `access_code` (required) |
| `invite_only` | One signed, single-use link per candidate | `candidate_list` |
| `email_code` | A 6-digit code emailed to the address entered, valid 10 minutes | |
| `sso` | The candidate's own school or company account | `allow_email_domains` |

Optional for every mode: `allow_email_domains` (globs, e.g. `*.ac.in`), `allow_ip_ranges` (CIDR, e.g. a lab network), `captcha` (default `true`).

Rate limits are applied per attempt and per test, never per IP address — a whole campus often shares one.

## `consent`

```json
"consent": {
  "version": "2026-10-01",
  "text": "This test records your answers, the times you open and leave the test window, …"
}
```

Shown before registration. The version and the time of acceptance are stored per candidate, so a later edit to the text stays distinguishable. Say what is collected, why, who sees it and for how long — and keep it true: if the test does not use the camera, say so.

## `registration_form`

An ordered list of fields. Each has an `id` (the results-CSV column key), a `type`, a `label`, optional `help`, and the two flags that matter most:

- `required: true` — blocks submission, with the message shown **on the field**
- `unique: true` — a second registration with the same value is refused. Put it on email, phone or roll number

| `type` | Candidate sees | `validation` keys used |
| --- | --- | --- |
| `short_text` | One-line box | `min_length`, `max_length`, `pattern`, `pattern_message` |
| `long_text` | Text area | `max_length` |
| `email` | Email box | `allowed_domains` |
| `phone` | Country code + number | `default_country` |
| `number` | Number box | `min`, `max`, `integer`, `decimals` |
| `date` | Date picker | `min`, `max` (as `YYYY-MM-DD`) |
| `dropdown` | Select list | `options` required |
| `radio` | One of several | `options` required |
| `checkbox` | Any of several | `options` required |
| `url` | Link box | `allowed_domains`, `check_reachable` |
| `consent` | Tick box with linked text | `link_text`, `link_target` |

Write a `pattern_message` for every `pattern`. "Invalid format" tells a nervous candidate nothing; "Format: 21CS0147 — two digits, two letters, four digits" tells them what to type.

Every rule is re-checked on the server. The browser's copy of it is a courtesy, not a control.

## `proctoring`

```json
"proctoring": { "profile": "standard", "overrides": { "violation_limit": 4, "violation_action": "warn_then_flag" } }
```

Pick a `profile` — `off`, `standard` or `strict` — then change individual controls in `overrides`. What each profile turns on is listed in the [PRD](PRD.md#proctoring-and-integrity).

| Override | Values |
| --- | --- |
| `desktop_only`, `require_fullscreen`, `block_copy_paste`, `watermark` | `true` / `false` |
| `require_camera`, `identity_photo`, `face_check`, `extra_monitor_check` | `true` / `false` (Strict controls) |
| `snapshot_interval_seconds` | ≥ 15 |
| `violation_limit` | A count, default 5 |
| `violation_action` | `warn_only`, `warn_then_flag`, `auto_submit`, `lock` |
| `allow_calculator` | `true` / `false` |

Browser checks deter and record; they cannot prove or prevent cheating — a second phone is invisible to all of them. Pariksha flags attempts for a human to judge and never disqualifies anyone by itself, except the `auto_submit` and `lock` actions an organiser explicitly chose.

## `scoring`

```json
"scoring": { "default_mode": "negative", "negative_fraction": 0.25, "pass_mark_percent": 50 }
```

`default_mode` applies to every question that does not set its own `scoring.mode`. The modes and their formulas are in [question-format.md](question-format.md#scoring-modes).

## `sections`

Each section has an `id`, a `title`, optional `instructions` and `time_limit_minutes`, `shuffle_questions`, and one `source`:

**Fixed** — everyone gets these questions in this order.

```json
{ "kind": "fixed", "questions": ["DIN-001", "DIN-002", "WRI-001", "WRI-002"] }
```

**Pool** — each candidate gets `count` questions drawn at random from the questions matching `filter`.

```json
{ "kind": "pool", "bank": "questions.json", "count": 4, "filter": { "tags": ["quantitative"], "difficulty": ["easy", "medium"] } }
```

**Sets** — several fixed papers, one handed to each candidate.

```json
{
  "kind": "sets",
  "assignment": "round_robin",
  "sets": [
    { "set": "A", "questions": ["LOG-001", "LOG-003", "LOG-005", "LOG-007"] },
    { "set": "B", "questions": ["LOG-002", "LOG-004", "LOG-006", "LOG-008"] }
  ]
}
```

`assignment` is `round_robin` (by registration order, so neighbours differ), `random`, `hash` (of the candidate ID, stable across attempts) or `from_candidate_list` (a `set` column in the uploaded CSV).

Publishing warns you if a pool holds fewer questions than `count`, or if sets drift apart in total points.

## `release`

```json
"release": { "when": "on_date", "at": "2026-11-16T18:00:00+05:30", "show": "score_and_sections" }
```

| `when` | |
| --- | --- |
| `never` | Candidates never see a score |
| `on_submit` | Shown on the finish page |
| `on_date` | Shown from `at` (required) |

| `show` | Candidate sees |
| --- | --- |
| `score_only` | Total and pass/fail |
| `score_and_sections` | Plus each section's score |
| `full_review` | Plus correct answers and explanations — use only after the test has closed for everyone |

## `retention`

```json
"retention": { "personal_data_days": 365, "snapshots_days": 90 }
```

A daily job deletes anything past its retention period and records the deletion in the audit log. Shorter is better: collect little, keep it briefly.

## Rules checked on import

The schema checks structure. The importer also checks:

- every question ID in a `fixed` or `sets` source exists in one of the `banks`
- a `pool` filter matches at least `count` questions
- section IDs and form-field IDs are unique within the test
- `access_code` is present when `mode` is `link_code`, and `at` is present when `when` is `on_date`
- `closes_at` is after `opens_at`, and `latest_start_at` falls inside the window
- every `options` list belongs to a `dropdown`, `radio` or `checkbox` field

Import is all-or-nothing: a file with any error imports nothing and returns every error with its position.

## Versioning

The format ID carries a major version (`@1`). Fields may be added within a major version, and importers ignore fields they do not recognise. Renaming or removing a field, or changing what one means, requires `@2`, a new schema file and a converter.
